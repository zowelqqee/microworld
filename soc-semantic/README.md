# soc-semantic — семантический слой для триажа алертов SOC

*Четвёртый порт одной и той же архитектуры, построенный и провалидированный на синтетических данных, пока реальный доступ был недоступен — теперь доступ подтверждённо работает: три реальных прогона нашли и исправили три реальных бага, а следующий за ними прогон впервые дошёл до дескриптивной статистики по реальным данным, которая теперь калибрует отдельный, более реалистичный синтетический генератор.*

Сделано в рамках тестового задания перед трудоустройством в SOC-команду T.Hunter. Тот же метод, что и в двух более ранних портах одной идеи — типизированные сущности, типизированные связи между ними, признаки, описывающие состояние этих связей в момент алерта — применённый сначала к [задаче AML], затем к [обнаружению сетевых вторжений], а теперь — к алертам SOC на базе Wazuh/OpenSearch.

**Статус: proof of concept, полностью провалидирован на синтетических данных; реальный доступ подтверждённо работает, три реальных прогона нашли и исправили три реальных бага, а дескриптивная статистика по реальным данным (шаг 6) теперь существует и калибрует под себя отдельный синтетический генератор — но реального precision/recall всё ещё нет.** Попытка 1 успешно скачала данные и упала на пробеле в правах при очистке; попытка 2, после этого фикса, скачала данные и построила отчёт о полноте полей на 188 946 документах, но упала на ошибке типа в timestamp при построении признаков; попытка 3, после *того* фикса, чисто прогнала отчёт о полноте полей на 30-дневном окне из 59 680 алертов и вскрыла самую крупную находку на сегодня — `rule.mitre.technique` на этом кластере хранит человекочитаемые названия техник ("System Owner/User Discovery"), а не ID MITRE ("T1033"), из-за чего скоринг молча обнулялся, а не только отчёт. Все три бага исправлены; после фикса оператор перезапустил тот же 30-дневный прогон, и он впервые прошёл до конца, включая шаг 6 — прямую дескриптивную статистику по признакам `sem_*` на реальных данных, без модели и без метки. Эти агрегаты (доли, среднее, медианы — никогда сырые записи) теперь калибруют [`soc_runtime/synthetic_v2.py`](soc_runtime/synthetic_v2.py), второй синтетический генератор рядом с оригинальным (см. [«Калибровка синтетики по реальным агрегатам»](#калибровка-синтетики-по-реальным-агрегатам)) — **это по-прежнему не precision/recall на реальных данных**, только более защитимая форма входа, на котором тестируется архитектура. Доступ к OpenSearch был недоступен, пока строилась архитектура и валидация ниже (см. [«Проблема, в цифрах самого SOC»](#проблема-в-цифрах-самого-soc) — почему доступ важен и что бы он подтвердил), и с тех пор подтверждённо заработал. Credentials предоставляет тот, кто запускает код, а не тот, кто его писал — поэтому каждое реальное подключение выполнял оператор, а не что-то, рассуждающее о схеме данных абстрактно — именно так каждая из трёх попыток нашла баг, который рассуждениями в одиночку найти было нельзя (см. [«Реальные данные»](#реальные-данные--предварительная-проверка-не-полная-валидация) про все три, включая ещё одну крупнейшую находку: `subject_user_name`, ключ сущности `actor`, вокруг которой построена вся архитектура, оказался пустым на **99,48%** реальных process-creation-алертов). Всё в разделах [«Валидация»](#валидация-только-синтетика) и [«Confidence router»](#confidence-router) — это проверка того, что архитектура ведёт себя так, как задумано, на контролируемом входе, а не утверждение о качестве на реальных алертах. Раздел [«Ограничения»](#ограничения) говорит об этом же ещё раз, в нескольких местах, намеренно.

## Проблема, в цифрах самого SOC

Этот раздел — единственное в README, что **не синтетика**. Это прямой пересказ того, что нашли 90-дневный отчёт о покрытии MITRE ATT&CK и ручной разбор ~20 закрытых инцидентов в реальном окружении, до того как был написан хоть один код.

| Находка | Число | Источник |
|---|---:|---|
| Алерты тактики Discovery, 90 дней | 19 162 | отчёт о покрытии MITRE |
| T1033 (System Owner/User Discovery) | 16 587 | отчёт о покрытии MITRE |
| T1082 (System Information Discovery) | 16 536 | отчёт о покрытии MITRE |
| T1105 (Ingress Tool Transfer) | 11 216 | отчёт о покрытии MITRE |
| T1059 (Command and Scripting Interpreter) | 11 203 | отчёт о покрытии MITRE |
| Корреляционные правила, регулярно закрываемые как false positive | *AD Enumeration Campaign, Lateral Movement Detection, Suspicious PowerShell Activity, Malware Campaign, Defense Evasion Burst* | ручной разбор ~20 закрытых инцидентов за несколько месяцев |

Причина закрытия в этих инцидентах неизменно звучала как вариация «массовый шум автокорреляции» — не «расследовано и подтверждено безобидным», а «слишком много, чтобы смотреть по одному». В этом и есть настоящая находка: высокообъёмные алерты одной MITRE-категории закрываются пачками потому, что сам объём делает их нерасследуемыми, а не потому, что кто-то подтвердил их безопасность.

**Гипотеза, которую проверяет прототип:** команды разведки в духе `whoami`/`systeminfo` и вызовы командных интерпретаторов используются примерно в равной мере легитимными администраторами и агентами инвентаризации ПО — и атакующими на этапе разведки. Тактика MITRE в обоих случаях одна и та же. Различается контекст — **кто** это запустил, **когда**, **как часто** и **в какой последовательности** — и ничего из этого контекста сегодня на алерте нет. Этот прототип — попытка добавить его туда.

Всё, что дальше — синтетика, потому что живого доступа к OpenSearch не было на момент разработки (проблема с сетевым доступом на стороне T.Hunter, по имеющимся сведениям решается). Числа выше — единственные в этом документе, взятые из реального окружения.

## Архитектура

### Сущности

| Сущность | Ключ | Что это |
|---|---|---|
| `actor` | `subject_user_name` + `subject_domain_name`, с fallback на `eventdata_user`, а затем на псевдо-идентичность по хосту — см. [находку по реальным данным](#subject_user_name-пуст-на-9948-реальных-алертов--находка-о-самой-архитектуре) | кто это сделал, либо лучшая доступная замена |
| `host` | `agent_name` | где это произошло |
| `actor_host` | (actor, host) | отношение этого actor к этой машине |
| `actor_technique` | (actor, technique) | отношение этого actor к этой технике, на всех хостах |
| `actor_host_technique` | (actor, host, technique) | полная тройка — срабатывала ли *именно эта* комбинация раньше |
| `process_chain` | (host, parent_image, image) | контекст запуска, когда доступны родитель/потомок из Sysmon |

### Признаки

12 признаков (плюс условный тринадцатый, см. ниже). Десять вычисляются каузально — по алертам строго до оцениваемого, затем сворачиваются в состояние — на скользящем или пожизненном окне; два (`sem_actor_identity_*`, добавлены после того, как первый реальный прогон нашёл `subject_user_name` почти всегда пустым — см. [находку](#subject_user_name-пуст-на-9948-реальных-алертов--находка-о-самой-архитектуре)) — прямые свойства полей самого текущего алерта, истории не требуют. У каждого признака — однострочное обоснование ниже; если для обоснования нужно было больше одного предложения, признак не прошёл отбор. Полная таблица со статистикой по каждому признаку на синтетическом корпусе: [`artifacts/semantic_catalogue.json`](artifacts/semantic_catalogue.json). Код: [`soc_runtime/semantic.py`](soc_runtime/semantic.py).

| Признак | Сущность | Смысл |
|---|---|---|
| `sem_freq_actor_host_technique_24h` | actor_host_technique | Сколько раз этот actor запускал именно эту технику именно на этом хосте за предыдущие 24 часа — признак повторяющегося, уже объяснённого паттерна против первого случая. |
| `sem_freq_actor_technique_7d` | actor_technique | Сколько раз этот actor запускал эту технику где угодно за предыдущие 7 дней — отделяет actor, чья роль — разведка, от того, кто её практически никогда не касается. |
| `sem_novel_actor_host_technique` | actor_host_technique | Запускал ли этот actor именно эту технику именно на этом хосте раньше, когда-либо в истории — самый сильный сигнал «мы это уже объяснили». |
| `sem_novel_host_for_actor` | actor_host | Видели ли этого actor на этом хосте раньше, независимо от техники. |
| `sem_novel_actor` | actor | Появлялся ли этот аккаунт в истории алертов до этого момента. |
| `sem_actor_time_typicality` | actor | Доля исторических алертов этого actor, попадающих в тот же бакет времени суток/выходного дня, что и текущий (со сглаживанием Лапласа) — низкая доля значит, что actor действует во время, которое для него практически нетипично. |
| `sem_actor_never_active_this_bucket` | actor | Есть ли у этого actor хоть один алерт (до сглаживания) в этом бакете времени суток/выходного дня — более резкий бинарный аналог сглаженной доли выше. |
| `sem_chain_tactic_diversity_15m` | actor_host | Сколько различных тактик MITRE этот actor вызвал на этом хосте за последние 15 минут, включая текущий алерт. |
| `sem_chain_discovery_to_escalation_15m` | actor_host | Последовал ли за алертом тактики Discovery от этого же actor/host алерт тактики Credential Access или Lateral Movement в пределах 15 минут — конкретная последовательность, которую аналитик назвал бы активным вторжением. |
| `sem_process_chain_novel_for_host` | process_chain | Встречалась ли именно эта пара родительский процесс → дочерний процесс на этом хосте раньше. |
| `sem_actor_identity_missing_subject` | actor | Был ли `subject_user_name` пуст на этом алерте, и пришлось ли identity переключаться на другое поле — на реальных данных это поле пусто на подавляющем большинстве алертов, так что сам факт его заполненности уже информативен. |
| `sem_actor_identity_host_fallback` | actor | Оказалось ли непригодным даже резервное поле identity, и пришлось ли identity actor схлопнуться до самого хоста — реальная потеря разрешения по «кто», а не косметическое значение по умолчанию. |

Тринадцатый признак, `sem_alert_technique_multiplicity` (сколько техник MITRE нёс сам алерт), появляется **только** в режимах обработки многозначного `rule.mitre.technique`, отличных от дефолтного — см. [соответствующий раздел](#многозначный-rulemitretechnique-находка-была-не-в-отчёте-а-в-состоянии). Он не безусловный намеренно: на однотехничном корпусе это константный столбец, а константный столбец всё равно сдвигает обученную логистическую регрессию (замерено на v1: PR-AUC 0,975616 → 0,975429), что молча переписало бы опубликованные числа. Там же — почему в этих режимах меняются значения ещё трёх признаков из таблицы выше.

### Защита от утечки идентичности

Перенесено из двух более ранних портов: **сырая идентичность никогда не попадает в значение признака.** Граф ключуется по именам actor, именам хостов и ID техник, но из `semantic.py` наружу уходят только агрегаты — `tests/test_semantic.py::test_no_feature_carries_raw_identity` проверяет, что каждая колонка `sem_*` числовая. Здесь это важнее, чем в сетевом порте: одна из двух популяций, которые этот датасет призван различать, — это конкретная фиксированная именованная служебная учётная запись (`svc-swinventory`), и признак, утекающий имя аккаунта, позволил бы модели запомнить «это конкретное имя → безобидно» вместо того, чтобы выучить паттерн частоты/новизны/времени, который и делает его безобидным — а это и есть весь смысл семантического слоя поверх lookup-таблицы.

### Причинность

Обеспечивается тем же способом, что и в сетевом порте: `test_features_never_read_the_future` пересчитывает слой на префиксе входных данных и требует побитового совпадения строк префикса. Если бы хоть один признак заглядывал вперёд, обрезка входа изменила бы более ранние строки.

### Baseline

[`soc_runtime/baseline.py`](soc_runtime/baseline.py) — намеренно не соломенное чучело. Он читает ровно те поля, что уже есть на дашборде покрытия MITRE — `rule.level`, one-hot по шести техникам с тегом Discovery, грубый бакет часа суток, флаг выходного — и больше ничего. Ни actor, ни host, ни истории. Это то, что видит сегодняшний триаж без контекста. Если бы преимущество семантического слоя перед этим испарилось — это и был бы честный результат для отчёта, а не повод ослабить baseline.

Одна странность, которую стоит назвать, а не спрятать: в наборе правил этого SOC техники T1059 (Command and Scripting Interpreter) и T1105 (Ingress Tool Transfer) помечены тактикой `Discovery` — канонически MITRE относит их к Execution и Command-and-Control соответственно. Это не баг прототипа; это отражает реальный 90-дневный отчёт о покрытии выше, и это ровно тот тип странностей корреляционных правил, с которым семантическому слою на уровне алерта приходится работать как есть.

## Синтетические данные

Доступа к OpenSearch пока нет, поэтому [`soc_runtime/synthetic.py`](soc_runtime/synthetic.py) генерирует 90-дневный поток алертов с той же схемой, что была бы у реальных алертов Wazuh (см. таблицу соответствия полей в docstring этого модуля). Запуск [`run_pipeline.py`](run_pipeline.py) с настройками по умолчанию сейчас даёт:

| | |
|---|---:|
| Алертов всего, 90 дней | 15 582 |
| Алертов `process_creation` (те, что скорит пайплайн) | 3 089 |
| Алертов `authentication` (фон для реализма, вне скоупа скоринга) | 12 493 |
| Помеченных синтетических аномалий | 210 (1,35% всех алертов, 6,8% алертов process-creation) |

**`is_synthetic_anomaly` / `synthetic_anomaly_type` — сфабрикованная разметка для прогона пайплайна. Это не утверждение о том, как выглядит реальная атака.** См. [«Ограничения»](#ограничения).

Всё в этом разделе и в [«Валидации»](#валидация-только-синтетика) ниже — про `synthetic.py` (v1), с параметрами, подобранными произвольно, до какого-либо реального доступа. Второй генератор, `synthetic_v2.py`, откалиброванный по реальным агрегатам, добавлен позже и рядом, не взамен — см. [«Калибровка синтетики по реальным агрегатам»](#калибровка-синтетики-по-реальным-агрегатам).

### Повторяющийся легитимный паттерн

Одна служебная учётная запись, `svc-swinventory`, каждый день обходит одни и те же 15 хостов, примерно в одно и то же раннее утреннее окно, запуская на каждом `systeminfo.exe`, затем `whoami.exe` — 2700 из 3089 алертов process-creation. Это намеренно самая громкая, самая повторяющаяся вещь в датасете: она должна быть тем, что сырой подсчёт техник видит как «16 587 алертов T1033», а семантический слой видит как один actor, делающий одно и то же, что и всегда. Поверх этого: пять учётных записей администраторов вручную запускают те же команды, не по расписанию, на своих хостах (179 алертов) — легитимно, но без жёсткого паттерна, и это более сложный случай для семантического слоя — не переоценить их как подозрительные.

### Внедрённые аномалии

Пять типов, подобранных так, чтобы каждый изолировал примерно один семантический сигнал, а не создавал один недифференцированный бакет «аномалия»:

| Тип | n | Изолирует | Что происходит |
|---|---:|---|---|
| `new_host` | 30 | новизна хоста | Известная учётная запись администратора на хосте, которого она раньше не касалась. |
| `off_hours` | 30 | типичность времени | Известная пара actor+host, в 00:00–04:00 или в 23:00 — время, которое этот actor никогда не использовал. |
| `new_actor` | 30 | новизна actor | Аккаунт, больше нигде не встречающийся в 90-дневном корпусе. |
| `manual_recon_chain` | 75 (25 последовательностей × 3) | частота + новизна | `whoami` → `net user` → `net group`, один shell, узкое окно, один хост — паттерн, явно названный в задании. |
| `tactic_escalation` | 45 (15 последовательностей × 3) | эскалация цепочки | Discovery → Credential Access (`T1003`) → Lateral Movement (`T1021`) в пределах ~10 минут, тот же actor/host. |

`T1003` и `T1021` существуют только для того, чтобы дать признаку эскалации что-то реальное для обнаружения; они не входят в шесть техник с тегом Discovery, которые валидация фактически скорит (см. `config.IN_SCOPE_TECHNIQUES` против записей только для эскалации в `TECHNIQUE_CATALOG`).

## Валидация (только синтетика)

**Читайте этот раздел как «делает ли архитектура то, для чего она спроектирована», а не как «насколько хорошо это сработает в продакшене».** Метка, которую предсказывает модель, написана тем же кодом, что сгенерировал данные. Модель, провалившая эту проверку, была бы реальной проблемой; модель, прошедшая её, взяла низкую планку, а не высокую.

Хронологическое разбиение, 70/30 по календарным дням (`soc_runtime/modeling.chronological_split`) — обучение на первых ~63 днях, тест на последних ~27, без перемешивания, так что модель не может увидеть более позднее повторение одной и той же тройки при обучении и быть спрошенной про более раннее на тесте. Один и тот же класс модели (`LogisticRegression`, `class_weight="balanced"`), один и тот же seed, один и тот же порог (0,50) для каждого arm. Полный отчёт: [`artifacts/validation_report.json`](artifacts/validation_report.json).

| Arm | Признаков | Precision | Recall | PR-AUC | Легитимных алертов помечено (ложные тревоги) |
|---|---:|---:|---:|---:|---:|
| baseline (сырые поля) | 12 | 0,567 | 0,833 | 0,710 | 42 / 898 (4,68%) |
| только semantic | 10 | 0,623 | **1,000** | **0,976** | 40 / 898 (4,45%) |
| raw + semantic | 22 | **0,795** | **1,000** | 0,973 | **17 / 898 (1,89%)** |

Тестовый набор: 964 алерта, 66 помеченных аномалий, 840 из которых принадлежат фиксированному паттерну инвентаризации ПО.

**На конкретно фиксированном по расписанию паттерне инвентаризации все три arm-а дают 0 ложных срабатываний (0/840).** Эта популяция оказалась отделимой уже сырыми `rule.level` + техникой + грубым бакетом часа суток, потому что она каждый день работает в узком, фиксированном раннем утреннем окне — так что эта метрика упирается в потолок и **не** сама по себе показывает преимущество семантического слоя. Она всё равно приведена, потому что это конкретно та популяция, о которой спрашивает задание.

**Различие видно на более широком показателе ложных срабатываний по «всем легитимным алертам» и по recall по типам аномалий**, там, где у baseline нет памяти, на которую можно опереться:

| Тип аномалии | n | recall baseline | recall semantic |
|---|---:|---:|---:|
| `off_hours` | 10 | 1,000 | 1,000 |
| `manual_recon_chain` | 30 | 0,900 | 1,000 |
| `tactic_escalation` | 5 | 0,800 | 1,000 |
| `new_actor` | 10 | 0,700 | 1,000 |
| `new_host` | 11 | 0,636 | 1,000 |

Baseline неплохо справляется с `off_hours` (у него есть сырой признак времени суток), но слабее всего именно там, где у него структурно нет вообще никакого сигнала — `new_host` и `new_actor` — потому что по конструкции он не несёт идентичности actor или host. Семантический слой, построенный специально для представления «видел ли я эту комбинацию actor/host/technique раньше», даёт по всем пяти типам recall 1,000 при этом пороге. Объединение обоих семейств признаков сокращает ложные тревоги на обычной (неповторяющейся) легитимной активности более чем вдвое относительно любого arm-а по отдельности, сохраняя recall на уровне 1,000 — та же форма «union доминирует», что нашли и AML-, и сетевой порты, хотя здесь разница получена на намного меньшем, синтетическом, самоисполняющемся тестовом наборе, и её надо взвешивать соответственно.

**Честная оговорка про коэффициенты.** В обученной модели arm-а semantic коэффициент `sem_process_chain_novel_for_host` — *отрицательный* (`-1,49`), несмотря на то что маргинальные средние по группам у этого признака идут в ожидаемом направлении (среднее 0,011 на повторяющемся паттерне против 0,361 на аномалиях). Скорее всего, это мультиколлинеарность: несколько признаков новизны срабатывают вместе на одних и тех же строках аномалий, и нерегуляризованная логистическая регрессия может присвоить отрицательный частный вес коррелированному предиктору, даже когда его маргинальный эффект положителен. На совокупную эффективность модели это не влияет, но отдельные коэффициенты здесь не стоит читать как изолированные причинные эффекты — полную таблицу коэффициентов см. в `artifacts/validation_report.json`.

## Confidence router

Находка, мотивирующая этот раздел, реальна, не синтетика: ручной разбор закрытых инцидентов T.Hunter нашёл несколько разных корреляционных правил — *AD Enumeration Campaign, Lateral Movement Detection, Suspicious PowerShell Activity, Malware Campaign, Defense Evasion Burst* — стабильно закрываемых как false positive, по шаблонной причине «шум автокорреляции» (см. [«Проблема»](#проблема-в-цифрах-самого-soc)). Это читается как структурная проблема с тем, что вообще эскалируется, а не разовый случай. **Confidence router** — один из способов это изменить: оставить сегодняшнее дешёвое сырое алертирование там, где оно уже уверено, и приберечь дорогое второе мнение — семантическую модель или человека — для алертов, где сырой сигнал по-настоящему неоднозначен.

Та же архитектура, что в [`ids-semantic/ids_runtime/router.py`](../ids-semantic/ids_runtime/router.py), перенесённая в этот домен. Код: [`soc_runtime/router.py`](soc_runtime/router.py).

```
raw_score вне полосы     ->  итог = raw_score          (semantic/union не запрашивается)
raw_score внутри полосы  ->  итог = secondary_score     (semantic, либо union)
```

**Без переобучения.** `modeling.fit_arms(train, test)` вызывается ровно один раз; `router.py` переиспользует модели raw/semantic/union из этого вызова для каждого варианта ниже, а не обучает свои. В отличие от сетевого порта, здесь нет кеша моделей на диске — `LogisticRegression` на ~2000 строк обучается за миллисекунды, так что кеширование добавило бы учёт без реальной экономии.

**Полоса подбирается на out-of-fold train-скорах, никогда на held-out наборе.** In-sample скоры на обучении оптимистичны — модель уже обучилась на этих строках. Вместо этого сырая модель переобучается на 4 расширяющихся хронологических фолдах обучающего набора (фолд 0 не даёт скорируемых строк, фолды 1–3 каждый скорится моделью, видевшей только более ранние фолды), и полоса подбирается по этим честным скорам. `tests/test_router.py::test_out_of_fold_scores_never_touch_the_test_set` и `test_router_band_is_fit_only_on_train_out_of_fold_scores` проверяют это структурно, а не по осмотру.

### Результат: реальный прирост precision, без прироста recall — и понятная причина почему

| Arm | Recall | Precision | PR-AUC | Routed |
|---|---:|---:|---:|---:|
| raw | 0,833 | 0,567 | 0,710 | — |
| semantic | **1,000** | 0,623 | **0,976** | — |
| union (raw+semantic) | **1,000** | 0,795 | 0,973 | — |
| router → semantic | 0,833 | 0,679 | 0,755 | 4,88% |
| router → union | 0,833 | **0,859** | 0,753 | 4,88% |
| router → union, наивная полоса [0,30, 0,70] | 0,864 | 0,695 | 0,747 | 14,52% |

Подобранная полоса при бюджете по умолчанию в 5% трафика на обучении: **[0,404, 0,883]**, покрывает 60,3% out-of-fold ошибок сырой модели на обучении (38/63) при 4,26% трафика обучения. Полная кривая: [`artifacts/router_results.json`](artifacts/router_results.json).

**Проверка на здравый смысл, сформулированная как вердикт, а не оставленная читателю** (та же дисциплина, что и проверка PR-AUC в ids-semantic): каждый вариант router-а **хуже** лучшего одиночного arm-а и по recall, и по PR-AUC. Recall `router->union` (0,833) не достигает 1,000 у semantic/union, а PR-AUC (0,753) не достигает 0,976 у semantic — склейка скоров двух моделей по порогу даёт худший *ранжирующий* результат, чем любая модель по отдельности, та же структурная причина, по которой router в ids-semantic не проходит свою проверку PR-AUC: вне полосы итоговый скор — это просто скор сырой модели, а её ранжирование (ROC-AUC 0,928) заметно хуже, чем у semantic (0,998). **Если алерты триажатся по скору, а не по фиксированному порогу, используйте semantic- или union-модель напрямую, а не этот router.**

**Почему recall не сдвигается, если точно:** 11 пропущенных аномалий сырой модели на тестовом наборе скорятся уверенно *низко* — 0,043, 0,217 (×7), 0,316 (×2), все заметно ниже нижней границы полосы 0,404. Полоса подбиралась так, чтобы захватить *ошибки* сырой модели out-of-fold на обучении при бюджете 5%, а эти ошибки кучкуются в диапазоне 0,40–0,88 — который, как оказалось, там, где у raw сидят **ложные срабатывания**, а не там, где эти уверенные ложноотрицательные. Router может спасти только ту ошибку, по которой готов запросить второе мнение; эти ошибки сырой модели никогда изначально не выглядят неуверенными. Это та же форма, что и находка Protocol A в ids-semantic («большинство ошибок raw — уверенные ошибки»), полученная независимо, на другом домене и другом классе модели.

**В чём router реально хорош: он подавитель ложных срабатываний.** `router->union` направляет на второе мнение 47 из 964 тестовых алертов (4,88%): 34 легитимных, 13 уже верно помеченных аномалий, 0 пропущенных аномалий. Из направленных алертов мнение union **исправило 33 и сломало 0** — превратило 33 ложные тревоги raw в верные не-алерты и не превратило ни одного верного решения в неверное. Precision прыгает с 0,567 у raw до 0,859 — *выше*, чем у самого union-always (0,795), потому что router запрашивает второе мнение только там, где raw уже была не уверена, а не на каждом алерте. **Это напрямую попадает в реальную мотивирующую проблему** — захлёбывание корреляционных правил в объёме ложных срабатываний — даже если это не закрывает разрыв по recall с прогоном semantic-модели на всём.

### По типам аномалий: идентично raw, и это не совпадение

| Тип | n | recall raw | recall semantic | recall router→union | доля направленных |
|---|---:|---:|---:|---:|---:|
| `off_hours` | 10 | 1,000 | 1,000 | 1,000 | 0% |
| `manual_recon_chain` | 30 | 0,900 | 1,000 | 0,900 | 13,3% |
| `tactic_escalation` | 5 | 0,800 | 1,000 | 0,800 | 20,0% |
| `new_actor` | 10 | 0,700 | 1,000 | 0,700 | 10,0% |
| `new_host` | 11 | 0,636 | 1,000 | 0,636 | 63,6% |

Recall у `router->union` **в точности равен recall у raw, по каждому типу, в каждой строке** — не приблизительно, а точно. `new_host` направляется на второе мнение чаще всего (63,6% — тип, в котором raw уверена меньше всего) и всё равно ничего не восстанавливает, потому что конкретные алерты `new_host`, которые raw *пропускает*, — не те, в которых raw не уверена; те, в которых raw не уверена по этому типу, — это те, что она и так угадывает верно. Routing улучшает precision внутри каждого из этих типов; он не трогает recall ни в одном из них, при этом бюджете, на этом тестовом наборе.

**Помог бы более широкий бюджет?** Частично, и недёшево. Развёртка бюджета (`band_frontier` в `artifacts/router_results.json`) показывает, что тестовый recall держится на 0,833 вплоть до бюджета 10%, немного подрастает до 0,864 при 20% (нижняя граница полосы наконец опускается достаточно, чтобы поймать два низкоскорящих промаха), и достигает 0,970 только при бюджете **50%**. В этой точке утверждение «направлять небольшую долю трафика на дорогой путь» уже неверно — половина потока алертов идёт на вторую модель, что убивает саму идею router-а. Разрыв по recall здесь — не проблема настройки; информация, нужная для пропущенных аномалий, не сконцентрирована рядом с границей решения так, как это предполагает router.

### Операционная стоимость, честно

Та же оговорка, что документирует ids-semantic, проверена напрямую для этого пайплайна: **доля направленных алертов — не та экономия вычислений, которой кажется.** `semantic.SemanticState` — это каузальный потоковый граф: `sem_freq_actor_host_technique_24h` для алерта *N* зависит от того, что каждый алерт до *N* уже свёрнут в это состояние. Нет способа узнать, какие алерты будут направлены на второе мнение, *до* вычисления семантических признаков для всех них — так что routing не может пропустить генерацию семантических признаков, только вызов инференса вторичной модели, который и так самая дешёвая часть.

| Измерено на этом корпусе (3089 алертов process-creation) | Время |
|---|---:|
| Генерация семантических признаков | ~4,6 мкс/алерт |
| Генерация baseline-признаков | ~1,6 мкс/алерт |
| Инференс сырой модели | ~0,03 мкс/алерт |
| Инференс union-модели | ~0,03 мкс/алерт |

Генерация семантических признаков стоит примерно в **160 раз** больше, чем вызов инференса модели — так что уводя 95% алертов от инференса union-модели, экономится стоимость, и так пренебрежимо малая на фоне стоимости генерации признаков, которую платит каждый алерт независимо от routing-а. **На масштабе этого корпуса это тайминги микросекундного уровня, определяемые накладными расходами Python/pandas на нескольких тысячах строк, а не продакшен-бенчмарк** — приведены ради формы аргумента (генерация признаков обязательна, инференс модели — то, что routing реально пропускает), а не как свидетельство о реальной стоимости инфраструктуры. Что *действительно* обобщается: если «дорогой путь» — это более тяжёлая модель, запрос к графу или аналитик-человек, а не второй вызов `LogisticRegression`, — доля направленных алертов и есть та доля трафика, что доходит *до этого*, и там ценность router-а реальна и совпадает с тем, что ids-semantic показывает на своих числах по CatBoost/сети.

### Что в итоге с router-ом

Работает наполовину, конкретным и объяснимым образом, как и разделение Protocol A/B в ids-semantic — там router Protocol B обошёл по recall все arm-ы, а Protocol A застрял ровно так же, как здесь. Здесь: **router — настоящий, измеренный подавитель ложных срабатываний, а не инструмент восстановления recall**, на этом синтетическом корпусе, при бюджете 5%. Это не пустяк — реальная проблема, с которой начинался этот раздел, это проблема объёма ложных срабатываний, и это прямое архитектурное свидетельство того, что идея «raw как дешёвый первичный фильтр, второе мнение только там, где он не уверен» решает именно эту проблему. Но это не свидетельство того, что router восстановит разрыв по recall между raw и постоянным semantic — потому что причина, по которой он этого здесь не делает, структурная (промахи raw уверенные, а не неуверенные), а не устранимая деталь реализации.

- **Попытка 2** (`--days 5`, после того фикса): шаги **[1/6]–[4/6] прошли полностью** на 188 946 реальных документах — аудит узлов, проверка безопасности объёма на 300 000 документов, само скачивание и полнота полей. **Шаг [5/6], построение признаков semantic + baseline, упал** с `TypeError: int() argument must be a string, a bytes-like object or a real number, not 'Timestamp'`. Исправлено — см. [«TypeError на timestamp»](#typeerror-на-timestamp-найден-на-втором-реальном-прогоне). Отчёт о полноте полей на шаге [4/6] — первая реальная находка на уровне признаков в этом документе, и она значима — см. [«subject_user_name пуст на 99,48% реальных алертов»](#subject_user_name-пуст-на-9948-реальных-алертов--находка-о-самой-архитектуре) ниже.
- **Попытка 3** (`--days 30`, после обоих фиксов): полнота полей прошла чисто — на этот раз без падения — на 30-дневном окне, 59 680 алертов process-creation. Отчёт показал `share_technique_in_the_six_scored: 0.0`: ни один из этих 59 680 алертов не совпал ни с одной из шести скорящихся техник прототипа. **Не отсутствие сигнала — несовпадение формата.** См. **Дескриптивной статистики (шаг 6) в этом документе пока нет нигде** — ни одна попытка не подтвердила, что до него дошла, так что реального распределения признаков `sem_*` для отчёта всё ещё нет, только числа полноты полей, которые уже произвели шаги 4 попыток 2 и 3. Дальше: что было найдено и исправлено рассуждениями о реальной схеме до всякого подключения, что нашла каждая реальная попытка подключения сама по себе, инструмент, построенный для следующего прогона, и что он расскажет, а что нет, когда завершится.

### Четвёртый источник: решение, а не молчаливый пробел

KES не входил в изначальный дизайн с тремя источниками (Sysmon process creation, Sysmon/Windows-аутентификация, сетевые алерты Suricata) — а Suricata, несмотря на то что была названа с самого начала, так и не была реализована даже в синтетическом генераторе (`synthetic.py` производит только строки Sysmon process-creation и аутентификации; см. [«Ограничения»](#ограничения)).

**Решение для этой итерации: вариант A — классифицировать и считать, не скорить.** `opensearch_client.classify_source` явно определяет документы KES (`data.KES.*`) и помечает их `event_category="kes_endpoint"` — не сворачивая молча в `"authentication"`, как делал код до того, как этот проход нашёл баг (любой документ без `data.win` проваливался в `"authentication"` по умолчанию; см. фикс в `opensearch_client.py` и `tests/test_opensearch_client.py::test_hit_to_row_kes_document_is_tagged_kes_endpoint_not_authentication`). Строки KES **видны и посчитаны** в каждом отчёте `real_data_check.py`, но не скорятся semantic- или baseline-слоем в этой итерации.

**Вариант B — отобразить собственные поля KES на схему actor/host/technique — отклонён для этой итерации.** Он потребовал бы разбора реальной таксономии событий KES: что KES называет «actor», несут ли его алерты теги MITRE вообще, что считается «technique» в его схеме. Ничего из этого не сделано. Угадывать это отображение под давлением реальных данных — это именно тот способ, которым семантический слой начинает молча скорить бессмыслицу без всякой валидации. Если покрытие KES когда-нибудь понадобится, оно заслуживает того же цикла проектирования, что получил Sysmon process-creation (см. [«Архитектуру»](#архитектура)), а не поспешной догадки по именам полей. Полное обоснование: раздел «Fourth source» в `config.py`.

### Что рассуждения о реальной схеме нашли и исправили, до подключения

Три реальных бага, найденных проработкой того, что подразумевает подтверждённая схема, а не прогоном на ней (что было невозможно):

1. **`semantic.py` вычислял образ процесса через `config.TECHNIQUE_CATALOG[technique]["image"]`** — таблицу поиска ровно с восемью синтетическими записями. Любой реальный ID техники MITRE вне этих восьми (то есть почти любой в реальном окружении) вызывал бы `KeyError`. Исправлено — теперь поле `image` алерта читается напрямую (реальное поле Sysmon, `data.win.eventdata.image`, которое синтетической схеме никогда не нужно было нести явно) — без обращения к каталогу. `tests/test_semantic.py::test_handles_mitre_technique_ids_outside_the_synthetic_catalogue` — регрессионный тест.
2. **`config.ALLOWED_CLUSTER_NODES` по умолчанию содержал два имени узлов синтетического генератора** (`office-collector`, `node01`). Реальные имена узлов этому коду не были известны — было подтверждено только имя `res-engineering-collector`, как то, которое нужно *исключить*. Оставь как есть — дефолт молча отфильтровал бы 100% реальных документов (не утечка, но фрейм, выглядящий в точности как «алертов на этой неделе нет», а не «неверный allow-list»). Исправлено двумя способами: allow-list теперь переопределяется через `SOC_ALLOWED_CLUSTER_NODES`, а `filters.filter_customer_data` теперь вызывает явную диагностику — с перечислением реальных имён узлов, которые увидел — если непустой fetch отфильтровывается до нуля строк, вместо того чтобы молча вернуть пустоту. `opensearch_client.discover_cluster_nodes` (запускается через `--discover-nodes-only`) — инструмент для поиска реальных имён, которые нужно туда вписать.
3. **`synthetic.generate_alerts()` по умолчанию завершал 90-дневное окно «сегодня»** (`pd.Timestamp.now()`), так что повторный запуск пайплайна в другой календарный день молча давал другой корпус — другое выравнивание будни/выходные, другие точные числа — несмотря на фиксированный seed. Не баг реальных данных, но найден в этом же проходе и стоил починки по той же причине: воспроизводимость. `config.SYNTHETIC_END_DATE` теперь фиксирует дату.

Ничего из этого не было найдено прогоном на реальных данных — доступа у этого кода на момент разработки не было. Это было найдено вопросом «что произойдёт, когда эта строка кода встретится со схемой, про которую мне только что сказали, что она реальная» — что является более слабой проверкой, чем реальный прогон, и это ровно то, почему важен [следующий раздел](#запуск-первой-реальной-проверки).

### Пробел в правах на `clear_scroll`, найден на первом реальном прогоне

Первый баг, который рассуждения до подключения не могли поймать, потому что дело не в форме данных — дело в том, какие именно вызовы API OpenSearch покрывают выданные права. `--days 5` на реальном кластере прогнал полное скачивание скроллом до конца (189 034 документа), а затем вызвал исключение:

```
opensearchpy.exceptions.AuthorizationException: AuthorizationException(403,
'security_exception', 'no permissions for [indices:data/read/scroll/clear]
and User [name=..., backend_roles=[kibanauser, readall], ...]')
```

У подтверждённого read-only пользователя (`kibanauser`, `readall`) нет `indices:data/read/scroll/clear` — отдельного, более узкого права, чем сам доступ на чтение данных, и его этому проекту никто не обещал. К моменту этого вызова все документы уже собраны; `client.clear_scroll()` — это серверная очистка scroll-контекста, и OpenSearch сам закрывает неиспользуемый контекст по истечении таймаута `"2m"`. Потеря уже скачанных данных из-за падения вызова очистки в блоке `finally` и была настоящим багом, а не сам отсутствующий доступ — пробел в правах ожидаем и корректен для read-only credentials.

**Фикс:** `opensearch_client._scroll` теперь отлавливает `AuthorizationException` конкретно вокруг вызова `clear_scroll`, печатает однострочную заметку (`note: clear_scroll skipped - read-only credentials lack indices:data/read/scroll/clear...`) и возвращает уже скачанные hits как обычно. Никакой другой тип исключения здесь не перехватывается — реальный сбой сети на `clear_scroll`, например, по-прежнему всплывает и по-прежнему валит прогон, как и раньше. В `tests/test_opensearch_client.py` три регрессионных теста: случай `AuthorizationException` возвращает все hits и печатает заметку, любое другое исключение по-прежнему всплывает, а обычный успешный путь не затронут и не печатает ничего лишнего.

### `TypeError` на timestamp, найден на втором реальном прогоне

С починенным `clear_scroll` `--days 5` прошёл скачивание (188 946 документов) и отчёт о полноте полей (шаг 4), затем упал внутри шага 5:

```
TypeError: int() argument must be a string, a bytes-like object or a real
number, not 'Timestamp'
```

**Реальный механизм оказался у́же, чем выглядел сначала, и стоит сформулировать его точно, а не принимать первую догадку.** Рабочая гипотеза на входе была «синтетика передаёт этому коду сырое число, реальные данные передают объект `Timestamp`». Прямое воспроизведение краша показало, что дело не совсем в этом — колонка из объектов `pandas.Timestamp` сама по себе прекрасно приводится к `int64`; pandas даёт ей настоящий dtype `datetime64`, и приведение — быстрая векторизованная операция. Настоящая причина: **разные источники алертов в одном и том же реальном батче форматируют поле `timestamp` с несовместимой информацией о UTC-смещении** — одни несут явное смещение, другие нет. Смешение timezone-*aware* и timezone-*naive* объектов `Timestamp` в одной колонке — это то, что pandas не может представить как единый dtype `datetime64`, и он откатывается на обычный dtype `object` — а `.astype("int64")` на колонке `object` откатывается на вызов Python-функции `int()` для каждого элемента по отдельности, что и вызвало исключение на объекте `Timestamp`. Подтверждено прямым воспроизведением до всякого фикса:

```python
>>> pd.DataFrame([{"timestamp": pd.Timestamp("2026-08-05T10:00:00.000Z")},
...                {"timestamp": pd.Timestamp("2026-08-05 10:05:00")}])["timestamp"].dtype
dtype('O')  # object, не datetime64 - это и есть форма, которая падает
```

**Фикс, по существу и в двух местах, а не `try`/`except` поверх симптома:**

1. `opensearch_client.hits_to_frame` теперь нормализует колонку `timestamp` к единому naive dtype `datetime64[ns]` (`pd.to_datetime(..., utc=True).dt.tz_localize(None)`) сразу после построения фрейма из сырых hits — в единственном месте, где собирается реальный батч, исправлено один раз, а не патчем в каждой точке использования ниже по цепочке. Это важно не только для `semantic.py`: `modeling.chronological_split` (`.dt.normalize()`) и `baseline.build_features` (`.dt.dayofweek`) оба используют pandas-аксессор `.dt`, который вызывает `AttributeError: Can only use .dt accessor with datetimelike values` на колонке dtype `object` — ещё два реальных места падения, в которые упёрлась бы та же форма со смешанными таймзонами, найденные проработкой последствий, а не наблюдением падений по одному.
2. `semantic._epoch_seconds`, новая небольшая функция со своими тестами, используется вместо голого вызова `.astype("int64")` и обрабатывает колонку `datetime64` (быстрый путь), колонку dtype `object`, смешивающую timezone-aware и -naive `Timestamp` (форма, которая реально упала), и обычную числовую колонку эпохи в секундах (исходная гипотеза, тоже обработана, поскольку это ничего не стоит) — все три проверены на совпадение для одного и того же момента времени.

`tests/test_semantic.py` (`_epoch_seconds` на всех трёх формах) и `tests/test_opensearch_client.py` (`hits_to_frame` на документах со смешанным форматированием UTC-смещения, вплоть до того, что `build_features` не падает) это покрывают.

### `subject_user_name` пуст на 99,48% реальных алертов — находка о самой архитектуре

Отчёт о полноте полей шага 4, первая реальная находка на уровне признаков в этом документе:

| Поле (алерты process-creation, n=10 480) | Доля пустых |
|---|---:|
| `subject_user_name` | **99,48%** (10 426) |
| `subject_domain_name` | **99,48%** (10 426) |
| `rule_mitre_technique` | 1,40% (147) |
| `rule_mitre_tactic` | 1,40% (147) |
| `image` | 0,52% (54) |
| `agent_name` | 0% (не выводится — инструмент печатает только поля с ненулевой долей пустых) |

**Это не крайний случай для прототипа, у которого каждая сущность ключуется на «кто это сделал».** `actor = subject_user_name + subject_domain_name` было первым предложением в таблице [«Сущности»](#сущности) этого проекта. Если это поле пусто на 99,48% алертов, которые оно должно ключевать, — архитектуру нужно переосмыслить, а не патчить обработку null, так что это и произошло, сформулировано прямо, а не смягчено.

**С полями host и technique всё в порядке.** Эта находка касается конкретно идентичности actor, а не общей проблемы качества реальных данных — `agent_name` (host) практически никогда не пуст, а `rule_mitre_technique`/`rule_mitre_tactic` пусты только на 1,40% алертов. Эта асимметрия напрямую формирует фикс ниже: host достаточно надёжен, чтобы быть настоящим fallback-ом последней инстанции, а не просто обнадёживающей догадкой.

**Почему это поле пусто, и что несёт ту же информацию вместо него — экспертное знание, а не то, что подтвердили данные этого прогона.** `subjectUserName`/`subjectDomainName` на событии создания процесса в Windows описывают учётную запись, которой *подсистема логирования* приписывает событие, а для очень многих событий process-creation это системная учётная запись, не человек — правдоподобная, хорошо задокументированная причина, почему это поле почти всегда пусто на алертах такого рода. Собственное поле Sysmon `User` (`data.win.eventdata.user`) — это *другое* поле с *другой* семантикой: контекст учётной записи, под которой выполняется *сам новый процесс*, что и имеет в виду аналитик SOC под «кто это запустил». `_resolve_actor` в `semantic.py` теперь проходит через три уровня fallback:

1. `subject_user_name`/`subject_domain_name`, когда пригодны.
2. `data.win.eventdata.user` (собственное поле Sysmon), разобранное из обычной формы `"DOMAIN\user"`, когда уровень 1 пуст.
3. Псевдо-идентичность по хосту, `"(host:<agent_name>)"`, когда непригодно ни одно поле — «кто» деградирует до «где». Каждый алерт с одного хоста без пригодной идентичности схлопывается в одного псевдо-actor-а. Это реальная потеря разрешения, переносимая во все признаки, ключуемые по actor, для этих строк, а не косметика по умолчанию, и `sem_novel_host_for_actor` в частности становится для них почти бессмысленным, поскольку actor и host в этом случае — одно и то же значение по построению.

Два новых бинарных признака фиксируют, какой уровень сработал — `sem_actor_identity_missing_subject` и `sem_actor_identity_host_fallback` (доводя семантический слой до 12 признаков) — исходя из того, что сам факт заполненности `subject_user_name` уже информативен на настолько разреженном поле, а не просто помеха парсинга, которую нужно спрятать. Оба — прямые свойства текущего алерта (истории не нужно), числовые, и не несут сырую строку идентичности — та же дисциплина, что и у любой другой колонки `sem_*`.

**Честно: реальная доля заполненности уровня 2 на этом кластере независимо не подтверждена.** У этого кода нет доступа к сырым документам — только числа полноты полей, которые произвёл собственный прогон оператора (таблица выше). `field_completeness` теперь также сообщает `actor_identity_fallback_coverage` — из алертов, которые `subject_user_name` не может идентифицировать, какую долю спасает `eventdata_user`, а не она откатывается до псевдо-идентичности по хосту — но этого числа тоже пока нет; оно появится после следующего реального прогона. Уровень 2 — это обоснованная, покрытая тестами на сфабрикованных данных реализация, готовая к измерению, а не подтверждённый фикс. Если окажется, что `eventdata_user` *тоже* в основном пуст на этом кластере, уровень 3 (fallback по хосту) уже и есть тот честный fallback последней инстанции, которым этот раздел и обещал быть, а не костыль, добавленный задним числом.

Синтетический генератор ничего из этого не задействует — `subject_user_name` там заполнен всегда, так что `eventdata_user` в синтетическом корпусе всегда `None`, а два новых признака — константный ноль, без эффекта на опубликованные синтетические числа валидации (подтверждено: каждая метрика в [«Валидации»](#валидация-только-синтетика) и [«Confidence router»](#confidence-router) не изменилась после этого фикса). Это само по себе ограничение, а не просто заявление о скоупе — синтетические данные были построены до того, как появилась эта находка, и не моделируют реальность, которую теперь должны бы моделировать.

### Названия техник, а не ID — находка третьего реального прогона

Отчёт о полноте полей попытки 3, на 30-дневном окне (59 680 алертов process-creation):

```
share_technique_in_the_six_scored: 0.0
```

Ноль. Не «низко» — ноль. **Это несовпадение формата, а не отсутствие активности Discovery.** Инсталляция Wazuh этого SOC записывает `rule.mitre.technique` как человекочитаемое *название* техники ("System Owner/User Discovery"), а не ID MITRE ("T1033"). Каждое сравнение, которое делает прототип с ID техники — `config.IN_SCOPE_TECHNIQUES`, `config.TECHNIQUE_CATALOG` — сравнивало название с ID и молча проваливалось, на каждом без исключения алерте.

**Это баг глубже, чем неверный отчёт.** То, что `real_data_check.field_completeness` неверно вычисляет `share_technique_in_the_six_scored`, — диагностическое неудобство. Но `modeling.restrict_to_scored_techniques` — функция, решающая, какие реальные алерты фактически скорят arm-ы semantic/baseline/router, — делает ровно то же сравнение `.isin(config.IN_SCOPE_TECHNIQUES)` с той же колонкой. Дойди реальный прогон до построения признаков и дескриптивной статистики до этого фикса, он бы молча заскорил **ноль** реальных алертов, без ошибки, без предупреждения — просто пустой результат, который легко можно было бы прочитать как «в этом окне нет активности Discovery», а не «формат не совпадает». Найдено по статистике отчёта до того, как это могло быть принято за реальный результат; сам баг пайплайна исправлен в тот же момент, не отложен на потом.

**Отображение, обоснованное источником, а не угаданное.** В 30-дневном окне встретилось 20 различных названий техник (по алфавиту, без частот). Каждое проверено индивидуально по официальной матрице MITRE ATT&CK Enterprise (<https://attack.mitre.org/techniques/enterprise/>):

Реализовано как `config.TECHNIQUE_NAME_TO_ID`, применяется `opensearch_client.translate_technique_name` в момент, когда реальный документ превращается в строку — так что `semantic.py`, `baseline.py`, `modeling.py` продолжают работать с ID ровно так, как задуманы, не подозревая, что был перевод. Значение, уже похожее по форме на ID, проходит без изменений (защитно — ничто не гарантирует, что каждая инсталляция Wazuh шлёт названия); название, отсутствующее в словаре, **тоже проходит без изменений**, а не отбрасывается и не зануляется — оно не совпадёт с `IN_SCOPE_TECHNIQUES` (никогда не будет заскорено, как и любая другая техника вне скоупа), но останется видимым в следующем отчёте `real_data_check.py`, в поле `unmapped_technique_names`, которое теперь отделено от `unscored_technique_ids` (реальный, корректно переведённый ID MITRE, который прототип просто не скорит — ожидаемо, не пробел) именно для того, чтобы актуальный случай не терялся среди ожидаемого.

**Два названия не удалось разрешить с уверенностью, и это не прикрыто ложной уверенностью:**

- **«Local Account»** — это буквальное название суб-техники, используемое без изменений сразу под тремя разными родительскими техниками: Account Discovery (`T1087.001`), Create Account (`T1136.001`) и Valid Accounts (`T1078.003`). Голая строка не может разрешить неоднозначность, кто сработал — только `rule.mitre.tactic` самого алерта, к которому в рамках этой работы не было доступа на уровне отдельного алерта, мог бы. Отображено сюда на `T1087.001`, потому что «Account Discovery» (родитель самой `T1087`) уже отдельно встречается в том же списке из 20 названий, а остальные 18 названий сильно смещены в сторону тактики Discovery, на которую нацелен весь прототип — это задокументированное обоснованное предположение, а не подтверждённый факт. `tests/test_opensearch_client.py::test_translate_technique_name_local_account_is_the_documented_judgment_call` фиксирует текущий выбор, чтобы будущее исправление было осознанной правкой, а не случайной.
- **«Tool»** вообще отсутствует в словаре. Нет ни одной MITRE Enterprise-техники с названием «Tool» — MITRE проводит чёткую границу между *Techniques* (поведением) и *Software* (инструментами/вредоносным ПО, используемыми для реализации этого поведения). Рассматривался и был отклонён вариант «Ingress Tool Transfer» (`T1105`), из-за пересечения по слову: совпадение по слову — не доказательство совпадения, а угадывание было бы ровно тем видом необоснованного отображения, которого всё это упражнение призвано избежать. Оставлено неотображённым намеренно, чтобы всплывать в отчёте о неотображённых названиях, а не исчезать в правдоподобно звучащем неверном ответе.

**Что это подтверждает про существующий скоуп из шести техник, осторожно:** четыре из двадцати названий совпадают с каталогом этого прототипа по ID MITRE в точности — `Account Discovery` → `T1087`, `Command and Scripting Interpreter` → `T1059`, `Remote Services` → `T1021` (техника только для эскалации) и `System Owner/User Discovery` → `T1033` — плюс собственные суб-техники `T1059` `PowerShell` и `Windows Command Shell` встречаются отдельно, всё это согласуется с той же реальной активностью, вокруг которой был спроектирован синтетический корпус прототипа. `T1082`, `T1069`, `T1105` и `T1003` (остальные четыре записи каталога) **не** встретились среди двадцати названий в этом конкретном 30-дневном окне — факт про это окно, а не утверждение, что они никогда не встречаются.

**Перевалидировано реальным повторным прогоном оператора: `share_technique_in_the_six_scored` действительно ушёл от `0.0`.** На том же 30-дневном окне (59 680 алертов process-creation) фикс поднял долю алертов, попадающих в шесть скорящихся техник, с **0%** (до фикса, из-за несовпадения название-против-ID) до **34,82%** — подтверждённое измерение, а не прогноз. Это же число — один из входов для калибровки синтетического генератора v2, см. [«Калибровка синтетики по реальным агрегатам»](#калибровка-синтетики-по-реальным-агрегатам).

### Бакет источника "unknown" (14,4%) — охарактеризован, но пока не объяснён

27 180 из 188 946 алертов (14,4%) классифицированы как `unknown` — не Sysmon, не Suricata, не KES и не Windows-аутентификация. Не исправлено, но и не проигнорировано: `real_data_check.unknown_source_sample` теперь собирает именно для этого бакета значения `decoder.name` и `rule.description`, а также форму (только *имена* полей, никогда значения) словаря `data` каждого документа — достаточно, чтобы на следующем прогоне назвать, что это за документы, без вывода сырого содержимого. Этого вывода пока не существует; отчёт этого прогона его не захватил, потому что инструмент не существовал до этого прохода.

**Правдоподобная, неподтверждённая гипотеза, сформулированная именно так:** четыре подтверждённые формы источников никогда не заявлялись как весь индекс целиком — деплой Wazuh нативно генерирует несколько других типов алертов, под которые прототип никогда не проектировался (события `syscheck`/целостности файлов, `rootcheck`, подключение/отключение агента, алерты vulnerability-detector, события active-response). 14,4%, попадающие в пятый-и-более бакет «прочих нативных типов алертов Wazuh», — скучное, вероятное объяснение — достаточно скучное, чтобы не показалось стоящим догадываться дальше без имён декодеров, по которым это можно проверить.

### Запуск первой реальной проверки

```bash
python -m soc_runtime.real_data_check --days 5
```

[`soc_runtime/real_data_check.py`](soc_runtime/real_data_check.py) — ограниченный, осторожный первый прогон, не `run_pipeline.py`. Он:

1. **Сначала проводит аудит `cluster.node`**, без фильтрации, и печатает каждое встреченное имя узла со счётчиком документов и меткой (`EXCLUDED` / `allowed` / `UNRECOGNISED`) — подтверждает, что `res-engineering-collector` действительно там есть, прежде чем доверять тому, что его исключение что-то значит, и сообщает, что именно вписать в `SOC_ALLOWED_CLUSTER_NODES`.
2. **Проверяет количество документов в окне до скачивания скроллом** (`opensearch_client.count_alerts`) и отказывается продолжать за пределами `config.REAL_DATA_COUNT_SAFETY_LIMIT` (300 000) или `config.REAL_DATA_MAX_WINDOW_DAYS` (14) без явного `--allow-large-window` — окно по умолчанию в 5 дней при ~40 700 документов/день должно дать около 200 000, комфортно ниже лимита; защита существует на случай опечатки вроде `--days 90`.
3. **Сообщает разбивку по типу источника** (Sysmon process-creation / Sysmon-auth / Suricata / KES / unknown) и сколько алертов несли многозначный `rule.mitre.technique` (сохраняется только первый — см. заметку в `opensearch_client.py`, почему, и это число — честный размер этого упрощения, не догадка). Когда есть алерты в `unknown`, также запускает `unknown_source_sample` — имена декодеров, описания правил и формы словаря `data` именно для этого бакета, только метаданные, никогда содержимое документа — см. [«Бакет источника "unknown"»](#бакет-источника-unknown-144--охарактеризован-но-пока-не-объяснён).
4. **Сообщает полноту полей** на подмножестве process-creation — доли пустых для `subject_user_name`, `eventdata_user`, `image`, `rule_mitre_technique` и т.д.; (поскольку третий реальный прогон нашёл названия техник там, где ожидались ID — см. [эту находку](#названия-техник-а-не-id--находка-третьего-реального-прогона)) `unmapped_technique_names` (значения, так и не переведённые ни в один ID MITRE — реальный пробел, требующий расширения `config.TECHNIQUE_NAME_TO_ID`), отдельно от `unscored_technique_ids` (реальные, корректно переведённые ID, которые прототип просто не скорит — ожидаемо); и (поскольку второй реальный прогон нашёл `subject_user_name` в основном пустым — см. [эту находку](#subject_user_name-пуст-на-9948-реальных-алертов--находка-о-самой-архитектуре)) `actor_identity_fallback_coverage`: из алертов, которые `subject_user_name` не может идентифицировать, какую долю реально спасает fallback `eventdata_user`.
5. **Запускает `semantic.build_features` + `baseline.build_features` внутри try/except** и сообщает реальное исключение, если оно возникло, вместо падения с сырым traceback — реальные данные почти наверняка содержат вариации полей, которых синтетический генератор никогда не производил.
6. **Сообщает дескриптивную статистику по значениям признаков `sem_*`** — среднее, медиану, долю ненулевых по каждому признаку, вычисленные напрямую (без обученной модели, без нужды в метке, поскольку новизна/частота/типичность считаются прямо из данных). Это честная проверка на здравый смысл, доступная без ground truth: выглядит ли форма правдоподобно, а не точна ли она.
7. Опционально (`--apply-synthetic-models`) **скорит реальные признаки моделями, обученными на синтетике**, с громкой пометкой «только иллюстративно» — см. строку-оговорку, которую возвращает сама функция. Ни при каких обстоятельствах не валидированный реальный скор.
8. Опционально (`--incidents incidents.json`) **сопоставляет конкретные закрытые инциденты**, уже известные вам (timestamp + host + rule id), с тем, что бы им присвоил семантический слой — ближайшая доступная вещь к реальной проверке гипотезы без API `/cases`. Этот репозиторий не поставляет никаких собственных данных об инцидентах (ID кейсов и timestamps ему никогда не передавались) — предоставьте свои; формат задокументирован в docstring модуля.

Каждое число, которое пишет `real_data_check.py` — в `artifacts/real_data_check_report.json` или в stdout, — это счётчик, доля или среднее. Credentials читаются из окружения и никогда не печатаются. Ничто в его выводе не требует пересылки куда-либо сырых данных построчно, чтобы обсудить результаты.

### Чего эта проверка не расскажет

Ни precision, ни recall, ни PR-AUC — на реальных строках нет `is_synthetic_anomaly`, и его не следует выдумывать. Чтение «выглядит правдоподобно по направлению» по дескриптивной статистике и опциональным иллюстративным скорам — это потолок того, что эта проверка может честно утверждать. Чтобы подняться выше этого потолка, нужна реальная разметка: либо более крупный ручной разбор закрытых инцидентов, чем уже просмотренные ~20, либо партнёрство с аналитиками для подтверждения/отклонения выборки того, что семантический слой будет помечать вперёд. До тех пор результаты [синтетической валидации](#валидация-только-синтетика) и [confidence router-а](#confidence-router) остаются единственными валидированными числами в этом документе — и остаются синтетическими.

## Калибровка синтетики по реальным агрегатам

**Что это и что это не.** [`soc_runtime/synthetic_v2.py`](soc_runtime/synthetic_v2.py) — второй, отдельный синтетический генератор, чьи параметры калиброваны по реальным агрегированным статистикам того же 30-дневного окна, что и находки в разделе [«Реальные данные»](#реальные-данные--предварительная-проверка-не-полная-валидация), а не подобраны произвольно, как параметры v1. **Это шаг к более защитимой *форме* синтетических данных, не замена реальной валидации и не утверждение, что числа ниже «лучше» v1-х.** [`soc_runtime/synthetic.py`](soc_runtime/synthetic.py) (v1) **не тронут** — ни код, ни уже опубликованные в этом документе результаты [«Валидации»](#валидация-только-синтетика) и [«Confidence router»](#confidence-router); v2 существует рядом, как дополнительный, явно опциональный корпус.

**Единственный вход — агрегаты, ничего персонального.** Ниже используются только доли, средние, медианы и счётчики — те самые, что уже приведены в разделе «Реальные данные» этого документа или прямо из него следуют. Ни одной сырой записи, имени, IP или конкретного хоста T.Hunter в этом генераторе нет — то же ограничение, которого придерживается весь остальной код в этом репозитории.

Большинство — в пределах разумной погрешности; два отклоняются заметнее и стоит сказать прямо, почему. `sem_novel_actor` (0,0007 против 0,0001) — обе величины уже настолько малы на корпусе такого размера (счёт различий на единицы событий), что дальнейшая подгонка настраивалась бы на шум, а не на сигнал. `sem_freq_actor_host_technique_24h` попал в верную качественную форму (медиана выше среднего — то же, что и в реальном измерении: небольшое число очень часто повторяющихся троек actor/host/technique тянет медиану вверх, длинный хвост редких троек тянет среднее вниз) и в верный порядок величины, но не в точное значение — `synthetic_v2.py` подбирает это одним «доминантным» actor/host/technique-паттерном плюс широким хвостом фиксированных низкочастотных троек (см. комментарий над `DOMINANT_DRIVERS` в коде), и дальнейшая точность потребовала бы больше сырых данных о форме распределения, которых операторский прогон не давал — не выдумывать их, а зафиксировать достигнутое как есть, было явным требованием этой задачи.

### Многозначный `rule.mitre.technique` (57,7%) — неожиданная находка, смоделированная явно

57,7% алертов process-creation в реальном 30-дневном окне несли **больше одного** значения `rule.mitre.technique` — одно правило корреляции пометило больше одной техники на одном алерте. Это выше, чем можно было бы ожидать заранее, и v1 никогда не моделировал этот случай вообще: `synthetic.py` — по построению один-технику-на-строку (см. docstring модуля), потому что был написан до того, как это стало известно.

`synthetic_v2.py` моделирует это явно, как отдельный, тестируемый шаг — `_maybe_multivalued(name, rng)`: с вероятностью `multi_valued_technique_share` возвращает `[name, other_name]` вместо `[name]`, где `other_name` — второе случайное название из того же пула техник. Этот список затем проходит через **тот же** `opensearch_client.first_of_multivalued`, что применяется к настоящим документам Wazuh при их превращении в строку — оставляется только первый элемент, остальное отбрасывается, ровно то упрощение, которое уже описано в docstring `first_of_multivalued`. `tests/test_synthetic_v2.py::test_multivalued_helper_rate_matches_real_share` проверяет саму частоту (50 000 сэмплов, измеренная доля 0,576 против цели 0,577) отдельно от полного генератора — именно потому, что на финальной колонке `rule_mitre_technique` эта многозначность уже необратимо схлопнута, и полный генератор её напрямую подтвердить не может.

**Это по-прежнему не то же самое, что реальная валидация.** Более реалистичная *форма* синтетики повышает доверие к тому, что архитектура тестируется на входе, статистически похожем на реальный, — она не производит ни одного реального прецедента, ни одной реальной метки атаки. `is_synthetic_anomaly` в v2 так же сфабрикован, как в v1; более резкое разделение semantic/union на v2 — это в первую очередь свойство того, как откалиброванный доминантный паттерн взаимодействует с искусственной меткой, а не подтверждение, что архитектура лучше находит настоящие атаки. Единственный способ узнать это — реальная разметка, см. [«Чего эта проверка не расскажет»](#чего-эта-проверка-не-расскажет).

**Оговорка, найденная позже и относящаяся к четырём `sem_*` целям в таблице выше:** они измерены на реальных данных кодом, который тогда оставлял от многозначного `rule.mitre.technique` только первое значение. То есть это статистика *вывода той свёртки*, а не свойство самих реальных алертов, и под исправленным режимом (следующий раздел) те же реальные данные дали бы другие числа. Калибровка v2 по ним корректна ровно в том смысле, что v2 сравнивался с реальностью в одинаковых условиях по обе стороны, — но перемеривать эти цели на реальных данных под исправленным режимом придётся заново, и до этого они остаются привязанными к режиму, а не абсолютными.

## Многозначный `rule.mitre.technique`: находка была не в отчёте, а в состоянии

57,7% реальных алертов process-creation несут больше одной техники MITRE. До этого раздела в схему попадала только первая (`opensearch_client.first_of_multivalued`). Разбираясь, чем именно это плохо, я нашёл, что проблема глубже, чем «в отчёте теряется часть тегов».

**`semantic.SemanticState` — это причинное потоковое состояние, и оно ключуется на `(actor, host, technique)`.** Каждый алерт не только *читает* из этого состояния, но и *сворачивается* в него для следующих алертов. Если у алерта отброшены все техники кроме первой, то:

- счётчики частоты для отброшенных техник никогда не инкрементируются;
- множества «видел ли я эту тройку раньше» их никогда не выучивают — поэтому более поздний алерт с техникой, которая уже срабатывала как *вторичная*, честно скорится как «никогда не виденный», хотя это неправда;
- `sem_chain_tactic_diversity_15m` — признак, чья единственная задача считать различные тактики, — структурно не может увидеть, что на одном алерте пришли Discovery и Execution сразу. Признак измеряет ровно то, что уничтожается до измерения.

Это дефект корректности состояния, а не вопрос богатства признаков, и он был бы дефектом даже если бы ни одна метрика от него не менялась. Регрессионные тесты на каждый из трёх пунктов — [`tests/test_multi_technique.py`](tests/test_multi_technique.py).

### Три режима, а не один «правильный»

Реализованы и сравнены на одинаковых условиях (`config.MULTI_TECHNIQUE_MODES`):

| Режим | Свёртка в состояние | Чтение признаков алерта | Признаков в semantic |
|---|---|---|---:|
| `first_only` | только первая техника | только первая | 12 |
| `primary_plus_count` (вариант A) | **все** техники и тактики | только первая, плюс `sem_alert_technique_multiplicity` | 13 |
| `aggregate` (вариант C) | **все** | все, со схлопыванием по каждому признаку | 13 |

`first_only` сохранён бит-в-бит как дореформенное поведение — иначе он не был бы честным baseline, и любое сравнение «до/после» на нём мерило бы сразу два изменения. Это закреплено тестом: под `first_only` результат идентичен независимо от того, несёт корпус многозначные колонки или нет.

**Про схлопывание в варианте C: `max` везде был бы неверен, и направление здесь важнее выбора функции.** Признаки не сонаправлены — высокая `sem_freq_*` означает «давно объяснённый повторяющийся паттерн» (в сторону легитимного), высокая `sem_novel_*` — «никогда не видел» (в сторону подозрительного). Схлопывание обоих через `max` брало бы частоту *самой обкатанной* техники, пряча редкую за шумной — ровно та потеря информации, ради устранения которой всё и затевалось. Поэтому `min` для частот, `max` для новизны: каждый признак сворачивается к своему наименее объяснённому концу. Это политика («если хоть одна техника на алерте выглядит необъяснённой, алерт стоит посмотреть»), а не факт о данных, и названа политикой намеренно.

**Вариант B (разворачивать алерт в N строк) сознательно не реализован.** На этом корпусе он раздул бы число строк примерно в 1,58 раза, считая одно реальное событие несколько раз, из-за чего все счётные метрики (`n_test`, число помеченных, бюджет трафика router-а) стали бы несравнимы с уже опубликованными без поправочного коэффициента, который сам требовал бы обоснования. Это законный дизайн — просто не тот, что можно честно сравнить с существующим baseline за один прогон, поэтому он назван и отложен, а не измерен наполовину.

### Что получилось: признаки исправились, метрики модели — нет

```bash
python -m soc_runtime.compare_multi_technique_modes
```

На откалиброванном корпусе v2 (57,2% многозначных среди тегированных алертов):

| Режим | `tactic_diversity` сред. | `novel_aht` сред. | `freq_24h` сред. |
|---|---:|---:|---:|
| `first_only` | 1,5007 | 0,002940 | 516,82 |
| `primary_plus_count` | **2,7664** | 0,002897 | 516,82 |
| `aggregate` | **2,9466** | 0,025638 | 230,98 |

**На уровне признаков фикс делает ровно то, для чего задуман, и это однозначно.** Средняя разнообразность тактик 1,50 → 2,77 — под `first_only` признак почти не видел множественности, теперь видит. `novel_aht` под вариантом A слегка *падает* (0,002940 → 0,002897) — это правильное направление: состояние теперь знает больше троек, поэтому реже ошибочно объявляет их новыми. Под вариантом C та же величина растёт в 8,7 раза (до 0,0256), потому что там любая новая техника на алерте помечает весь алерт новым — это не ошибка, это заявленная политика C в действии.

| Режим | arm | Precision | Recall | PR-AUC |
|---|---|---:|---:|---:|
| `first_only` | semantic | 1,0000 | 1,0000 | 1,0000 |
| `first_only` | union | 1,0000 | 1,0000 | 1,0000 |
| `primary_plus_count` | semantic | 1,0000 | 1,0000 | 1,0000 |
| `primary_plus_count` | union | 1,0000 | 1,0000 | 1,0000 |

**А на уровне метрик модели фикс не улучшает ничего, и это надо сказать прямо.** Вариант A даёт ровно те же числа, что и baseline. Вариант C роняет recall с 1,000 до 0,857 — но в тестовом наборе v2 всего **7** положительных примеров, так что это разница в один алерт, и читать её как реальную регрессию нельзя ровно так же, как нельзя было бы читать обратную разницу как улучшение. Метрики semantic/union на этом корпусе упёрлись в потолок (precision/recall/PR-AUC = 1,0 у двух режимов из трёх): **при 7 положительных примерах и полном разделении эти метрики просто не способны различить режимы.** Это ограничение измерения, а не свидетельство в пользу какого-либо варианта.

Контрольный прогон на v1 (одна техника на алерт по построению) даёт одинаковые precision/recall во всех трёх режимах, с расхождением PR-AUC в 4-м знаке (0,9756 против 0,9754) исключительно от добавления константного столбца — подтверждение, что сама механика режимов ничего не ломает там, где чинить нечего.

### Что выбрано и почему — не по числу

Для реального пути данных (`config.REAL_DATA_MULTI_TECHNIQUE_MODE`) выбран **вариант A, `primary_plus_count`**. Обоснование архитектурное, потому что метрического обоснования эти данные дать не могут:

- он исправляет продемонстрированный дефект — повреждение причинного состояния, то есть собственно баг;
- он не переопределяет молча смысл существующих признаков. Вариант C меняет значение трёх признаков сразу, а вся дескриптивная статистика по реальным данным (включая цели калибровки выше) измерена под старым чтением — принять C значило бы обесценить эту базу без нового реального прогона, на котором её можно перемерить;
- его дополнительный сигнал аддитивен и интерпретируем («алерт нёс N техник»), а не является переинтерпретацией уже имеющихся;
- политика C («любая необъяснённая техника → подозрительно») правдоподобна, но это именно неподтверждённое допущение, а реальной разметки, на которой его можно проверить, не существует. Меньшее изменение, устраняющее доказанный баг, предпочтительнее большего, добавляющего непроверенную политику.

**Глобальный дефолт остаётся `first_only`** — по одной причине: это единственный режим, под которым опубликованные выше числа v1 воспроизводятся бит-в-бит (проверено; включая коэффициенты). У v1 многозначных алертов нет вообще, так что там режим не меняет ничего, кроме появления константного столбца, — а этот столбец, как показано выше, сдвигает PR-AUC в 4-м знаке. Реальный путь (`real_data_check.py`) под этот дефолт не подпадает и работает под исправленным режимом, потому что именно там 57,7% и именно там неверная свёртка чего-то стоит.

### Честно о том, что это не решило

Исходная гипотеза, с которой задача ставилась, — что падение precision на реалистичной синтетике вызвано именно потерей информации при «взять первую технику» — **не подтвердилась**. Устранение потери информации (обоими способами) не сдвинуло precision вообще: она и до, и после равна 1,0000 на v2. Причина расхождения arm-ов между v1 и v2 лежит в другом месте — в плотности аномалий (0,1% против 6,8%, см. [предыдущий раздел](#честное-сравнение-через-полный-пайплайн-v1-против-v2)), а не в многозначности тегов.

Более общо: **реальные данные T.Hunter содержат существенную долю неоднозначных, многотехничных алертов — это структурная сложность самих данных, а не баг реализации, и она не «чинится» тем, что её перестали игнорировать.** Обработка стала корректной; количество техник на алерте от этого меньше не стало. Что действительно даёт исправление — это состояние, которое больше не недосчитывает, и признак разнообразия тактик, который наконец измеряет то, что заявляет. Насколько это влияет на реальный триаж, эти синтетические числа сказать не могут, и притворяться иначе значило бы выдать корректность за эффективность.

- `config.ALLOWED_CLUSTER_NODES` — это **allow-list**, а не просто block-list — узел, добавленный в кластер после написания этого файла, исключён по умолчанию, а не включён по умолчанию. По умолчанию содержит два имени узлов *синтетического* генератора (`office-collector`, `node01`), которые не совпадут с реальным кластером — для скачивания реальных данных нужно явно задать `SOC_ALLOWED_CLUSTER_NODES` (см. [«Подключение к реальным данным»](#подключение-к-реальным-данным)). `filters.filter_customer_data` вызывает исключение, а не возвращает молча пустой фрейм, если allow-list отбрасывает каждую строку непустого fetch-а — тот самый режим сбоя на реальных данных, для которого это различие и существует.
- Сам запрос к OpenSearch исключает его (`must_not`-условие в `opensearch_client._build_query`).
- `filters.filter_customer_data` фильтрует ещё раз на выходе из любого источника данных, а `filters.assert_no_excluded_nodes` вызывает `CustomerDataError` — не предупреждение — если он вообще когда-либо обнаружится во фрейме ниже по цепочке.
- Синтетический генератор никогда его не производит: `synthetic.generate_alerts` проверяет это в своём собственном выводе.
- `opensearch_client.discover_cluster_nodes` — это read-only, только-агрегатный инструмент аудита (`{имя_узла: количество_документов}`) для подтверждения, что узел реально присутствует на реальном кластере, прежде чем доверять тому, что его исключение вообще что-то значит.
- `tests/test_filters.py`, `tests/test_synthetic.py` и `tests/test_opensearch_client.py` проверяют всё вышеперечисленное напрямую, на сфабрикованных документах (у этого кода нет живого подключения).

## Ограничения

- **Каждое число валидации в этом документе — синтетическое.** Метка написана тем же кодовым путём, что сгенерировал признак, который её предсказывает, так что сильный результат здесь — слабый (но не нулевой) сигнал, а слабый результат был бы реальной проблемой. Это говорит, что пайплайн работает от начала до конца и ведёт себя так, как задуман; это ничего не говорит о реальном качестве детекции.
- **Синтетические паттерны аномалий — упрощённые догадки, не смоделированное поведение атакующего.** Они кодируют прочтение одним аналитиком пяти паттернов, описанных в задании (новый хост, нерабочее время, новый аккаунт, цепочка ручной разведки, эскалация тактики), а не эмпирические данные о том, как реально выглядят вторжения в этом окружении. Реальный атакующий, адаптирующийся к защите, вознаграждающей «типичное время» и «типичные хосты», не обязательно произведёт алерты, похожие на любую из этих пяти форм.
- **Метрика ложных срабатываний на повторяющемся легитимном паттерне упёрлась в потолок (0/840 для каждого arm-а)**, потому что синтетическое расписание инвентаризации достаточно узкое и фиксированное, чтобы его отделял уже сырой час суток — см. [«Валидацию»](#валидация-только-синтетика). Это конкретное число не стоит читать как доказательство необходимости семантического слоя; именно более широкие числа по легитимным алертам и по типам аномалий — те, что различают arm-ы.
- **Нет глубины дерева процессов дальше одного родителя.** `process_chain` использует `parentImage`/`parentCommandLine` напрямую и не идёт дальше вверх по цепочке предков через `parentProcessGuid`, что поддерживают реальные данные Sysmon и что, вероятно, стоило бы использовать продакшен-версии.
- **Новизна и частота ограничены потоком алертов process-creation/technique, который потребляет прототип, а не полной историей идентичности или аутентификации**, которая была бы доступна реальному деплою (например, история логинов аккаунта генерируется для реализма, но никогда не сопоставляется с новизной actor).
- **Одна популяция actor/host, один часовой пояс, одна оргструктура.** В реальных окружениях несколько офисов, сменная работа, подрядчики с легитимно нерегулярными часами и служебные аккаунты, которые *не* привязаны к одному обходу пятнадцати хостов инвентаризации. Признаки временно́й типичности и новизны потребовали бы повторной валидации на этом разнообразии, а не просто на бо́льшем объёме синтетики.
- **Адаптер OpenSearch подключался к живому кластеру оператором (credentials никогда не передавались тому, кто писал этот код) четыре раза на сегодня — три нашли и исправили реальный баг, четвёртый впервые дошёл до шага 6.** Попытка 1 скачала 189 034 документа и упала на пробеле в правах `clear_scroll`; попытка 2, после этого фикса, прошла аудит узлов / проверку объёма / скачивание / полноту полей на 188 946 документах и упала на `TypeError` в timestamp при построении признаков; попытка 3, после того фикса, чисто прогнала полноту полей на 59 680 алертах за 30-дневное окно и нашла `share_technique_in_the_six_scored: 0.0` — не отсутствие активности, а несовпадение формата название-против-ID, которое молча обнуляло сам scoring-пайплайн (`modeling.restrict_to_scored_techniques`), а не только этот отчёт; после этого фикса повторный прогон на том же окне впервые дошёл до конца, включая шаг 6 — прямую дескриптивную статистику по `sem_*` без модели и без метки. Все три бага исправлены — см. [«Пробел в правах на clear_scroll»](#пробел-в-правах-на-clear_scroll-найден-на-первом-реальном-прогоне), [«TypeError на timestamp»](#typeerror-на-timestamp-найден-на-втором-реальном-прогоне) и [«Названия техник, а не ID»](#названия-техник-а-не-id--находка-третьего-реального-прогона). **Дескриптивная статистика по реальному окну теперь в этом документе есть** — см. [«Калибровка синтетики по реальным агрегатам»](#калибровка-синтетики-по-реальным-агрегатам) — но это по-прежнему только доли/средние/медианы шести признаков и полноты полей, не полный дамп, не precision/recall, и не гарантия, что каждое несовпадение схемы уже найдено; крайние случаи пагинации и всё, что не покрывают именно эти агрегаты, остаются открытыми.
- **`subject_user_name` пуст на 99,48% реальных алертов process-creation, и реальная доля заполненности собственного fallback-поля фикса пока не подтверждена.** Это крупнейшая находка по реальным данным на сегодня — первичный ключ сущности `actor` оказался почти непригоден, а не крайний случай. См. [полный разбор](#subject_user_name-пуст-на-9948-реальных-алертов--находка-о-самой-архитектуре) про трёхуровневый fallback, почему уровень 2 (`data.win.eventdata.user`) должен помочь исходя из реальной семантики полей Windows Event Log, и явную оговорку, что у этого кода нет доступа к сырым документам, чтобы подтвердить, насколько часто это реально работает.
- **`rule.mitre.technique` хранит названия техник MITRE, а не ID, и это молча обнуляло scoring-пайплайн до фикса.** 20 реальных названий проверены индивидуально по официальному справочнику MITRE ATT&CK и переведены в момент, когда реальные данные входят в пайплайн; два (`"Local Account"`, `"Tool"`) не удалось разрешить с полной уверенностью, и это задокументировано именно так, а не угадано. Подтверждено реальным повторным прогоном: доля алертов в шести скорящихся техниках ушла с 0% до **34,82%** на том же 30-дневном окне. См. [«Названия техник, а не ID»](#названия-техник-а-не-id--находка-третьего-реального-прогона).
- **14,4% реальных алертов (27 180 из 188 946) классифицируются как источник `unknown` — охарактеризовано, но не объяснено.** Имён декодеров и описаний правил для этого бакета в этом документе пока нет; инструмент для их сбора (`unknown_source_sample`) есть. См. [«Бакет источника "unknown"»](#бакет-источника-unknown-144--охарактеризован-но-пока-не-объяснён).
- **KES (Kaspersky Endpoint Security) в этой итерации виден и посчитан, но не скорится** — осознанное решение (вариант A), не молчаливый пробел. См. [«Четвёртый источник»](#четвёртый-источник-решение-а-не-молчаливый-пробел) про обоснование; Suricata в том же нескорящемся положении, несмотря на то что была названа в изначальном дизайне, потому что так и не была реализована даже в синтетическом генераторе.
- **Логистическая регрессия, не реальные корреляционные правила в продакшене.** Это валидирует, разделяют ли *признаки* две популяции, а не то, изменит ли их подключение к «AD Enumeration Campaign» или «Suspicious PowerShell Activity» долю ложных срабатываний конкретно этих правил — для этого нужна реальная логика корреляционных правил, к которой у прототипа нет доступа.
- **Реального precision/recall пока не существует, и ничего не сфабриковано, чтобы заполнить этот пробел.** [«Реальные данные»](#реальные-данные--предварительная-проверка-не-полная-валидация) охватывает, что честно может, а что не может утверждать чисто дескриптивная проверка без ground truth. Первая задача после того, как реальный доступ будет задействован, — повторная валидация на реальной, основанной на инцидентах разметке, а не деплой чего-либо из этого репозитория на основании синтетических чисел.
- **Confidence router не восстанавливает разрыв по recall между raw и постоянным semantic, и причина структурная, а не промах настройки.** См. [«Confidence router»](#confidence-router) — собственная проверка на здравый смысл router-а показывает его хуже лучшего одиночного arm-а и по recall, и по PR-AUC, прямо в таблице результатов, а не сглажено.
- **57,7% реальных алертов несут несколько техник MITRE одновременно, и до фикса это повреждало причинное состояние, а не только отчёт.** Исправлено: состояние теперь сворачивает все техники и тактики. Но исправление **не улучшило ни одной метрики модели** — вариант A даёт числа, идентичные baseline, вариант C роняет recall на один алерт из семи. Метрики на v2 упёрлись в потолок (7 положительных примеров, полное разделение), поэтому выбор режима сделан по архитектурным основаниям, а не по числам, и это прямо сказано в [соответствующем разделе](#многозначный-rulemitretechnique-находка-была-не-в-отчёте-а-в-состоянии). Многотехничность реальных алертов — структурное свойство данных; оно не устраняется тем, что его перестали игнорировать.
- **Четыре реальные `sem_*` цели в `config.REAL_CALIBRATION_TARGETS` измерены под старым, однотехничным режимом** и потому описывают вывод той свёртки, а не свойство реальных алертов как таковых. Под исправленным режимом их надо перемерить на реальных данных; до тех пор они привязаны к режиму, а не абсолютны.
- **`synthetic_v2.py` калиброван по сводным моментам (доли, среднее, медиана шести признаков), не по полным распределениям — операторский прогон их и не мог дать.** «Достигнуто» в [«Калибровка синтетики по реальным агрегатам»](#калибровка-синтетики-по-реальным-агрегатам) — это близкое совпадение по нескольким числам, не проверка формы всего распределения; более резкое разделение arm-ов semantic/union на v2 по сравнению с v1 — это в первую очередь следствие того, как откалиброванный доминантный actor/host/technique-паттерн взаимодействует со сфабрикованной меткой аномалии на корпусе такого масштаба, а не подтверждение, что архитектура стала точнее находить настоящие атаки. Число внедрённых синтетических аномалий (54) в v2 не масштабировано пропорционально четырёхкратно выросшему объёму легитимного фона — осознанный выбор (реальные агрегаты ничего не говорят о частоте настоящих атак, это не то, что можно откалибровать), но именно из-за него тестовый набор v2 несёт долю аномалий на два порядка ниже, чем у v1 (0,1% против 6,8%), и метрики semantic/union на v2 посчитаны всего на 7 положительных примерах — см. [«Честное сравнение через полный пайплайн»](#честное-сравнение-через-полный-пайплайн-v1-против-v2).

## Запуск

```bash
pip install -r requirements.txt
python run_pipeline.py          # синтетический источник v1, полное воспроизведение
python -m pytest tests -q       # 195 тестов, без сети, без реальных данных

# v2, откалиброванный по реальным агрегатам, и честное сравнение с v1:
python -m soc_runtime.synthetic_v2                    # только генератор + достигнутая калибровка
python -m soc_runtime.compare_synthetic_versions       # полный пайплайн v1 vs v2, см. раздел выше
python -m soc_runtime.compare_multi_technique_modes    # три режима обработки многозначных техник

# Реальные данные (сначала см. раздел «Реальные данные» выше):
SOC_DATA_SOURCE=opensearch python -m soc_runtime.real_data_check --discover-nodes-only
SOC_DATA_SOURCE=opensearch python -m soc_runtime.real_data_check --days 5
```
